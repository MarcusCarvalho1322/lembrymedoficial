# Onda 2 — Diagnóstico de Erros, Bugs e Gaps

**Auditoria forense LEMBRYMED — 22/04/2026**

Severidades usadas:
- **🟥 Crítica** — risco de vida, vazamento PII, falha total de fluxo crítico ou exploit OWASP Top 10 ativo
- **🟧 Alta** — bug funcional em fluxo principal, violação LGPD, falha de segurança explorável
- **🟨 Média** — UX quebrada, performance ruim, código frágil
- **🟦 Baixa** — melhoria estética, refactor de limpeza

Legenda "Ação":
- **AUTO** — posso corrigir autonomamente na Onda 3
- **APROVAR** — preciso da sua aprovação antes de executar
- **INFRA** — depende de ação externa (Vercel/Railway dashboard, Neon migration em produção, etc.)

> **Observação sobre ferramentas automatizadas:** `npm install` não completa nesta máquina por dois problemas:
> 1. OneDrive/Windows EPERM ao deletar `node_modules/send` (permissões)
> 2. Package-lock referencia `esbuild@0.27.7` (via `tsx@4.21.0`) — **essa versão não existe no registry npm**. Bug real, documentado em **INFRA-21** abaixo.
>
> Sem install local, não consigo rodar `tsc`, `npm run build`, `npm audit`. Isso **não bloqueia** o diagnóstico (análise estática é suficiente), mas quando a Onda 3 executar correções, primeiro precisamos consertar o lockfile (ver INFRA-21).

## Observações arquiteturais adicionais

### IDOR — "risco #1" nesta stack?

O prompt inicial marca IDOR como risco máximo. Na arquitetura real do LembryMed, o risco **não é IDOR clássico** porque:
- Paciente **não tem UI/endpoints autenticados**. Interage só via WhatsApp.
- Admin é **single-user** (Marcus). Não há escopo por usuário-admin, só "admin ou não admin".

O risco **equivalente** aqui é:
- **Spoofing de telefone** no webhook Z-API: atacante conhece o telefone de um paciente, forja webhook, marca confirmações falsas. Mitigado pelo token de webhook (item 02).
- **Entrada de mensagem por outro paciente**: uma vez que o match é por `phone`, dois pacientes com números invertidos (erro de cadastro) podem ver/responder por outro. Mitigado pelo `unique constraint` em `patients.phone`.
- **Comprometimento de admin**: risco muito maior que IDOR neste app. Todos os itens 01/02/04/10 visam reduzir essa superfície.

### Webhooks Z-API e Stripe — assinatura/idempotência

| Webhook   | Validação origem                         | Dedup                       |
|-----------|------------------------------------------|-----------------------------|
| Stripe    | ✅ `stripe.webhooks.constructEvent` (HMAC) | ❌ (ver item 40)            |
| Z-API     | ⚠️ opcional via `ZAPI_WEBHOOK_TOKEN`       | ✅ Redis SET NX TTL 5 min   |

### Stack Neon e autorização (relevante ao prompt)

O prompt alerta: "Neon puro não tem RLS; autorização é responsabilidade do backend". **Confirmado.** Porém, como acima, não há modelo multi-tenant por paciente — o backend filtra por `patientId` apenas em workers / webhook / query admin (admin vê tudo, é esperado). Não há "paciente A tentando ler dados do paciente B" pela UI web — não existe UI de paciente.

### Se/quando criar painel do paciente (Onda 4+)

Se no futuro um paciente autenticar no web (ex: dashboard próprio), TODAS as queries precisarão incluir `WHERE patient_id = session.patient_id`. Hoje essa hipótese está fora de escopo, mas já ficou na cabeça de quem projeta: **toda rota deveria receber `req.patient.id` via middleware, não por param do cliente**.
